1. PROJECT INTENTION
====================

Project name:
SharedNav

Full title:
SharedNav — Collaborative Multi-Robot Navigation and Shared Environment Awareness in ROS 2

Main research question:
Can two autonomous mobile robots explore an initially unknown environment more efficiently by sharing environmental information and coordinating exploration goals instead of behaving independently?

Secondary research question:
Can heterogeneous sensor information contributed by different robots improve the shared representation of the environment and enable one robot to act on information detected by another robot?

Core demonstration:
Two TurtleBot-like mobile robots operate inside a simulated indoor environment.

Robot 1:
- 2D LiDAR
- odometry
- SLAM
- Nav2
- obstacle detection

Robot 2:
- 2D LiDAR
- odometry
- SLAM
- Nav2
- camera or RGB-D / depth sensor if time permits
- optional semantic object detector

Both robots:
- maintain separated ROS 2 namespaces
- maintain separated TF trees
- navigate autonomously
- contribute environmental information
- receive coordinated exploration goals

A central coordination layer:
- tracks robot state
- receives maps / world information
- detects or receives exploration frontiers
- assigns unique exploration goals
- avoids sending both robots to the same frontier
- optionally detects path conflicts
- optionally maintains semantic object observations

The expected final behavior is:

1. Both robots start in an unknown environment.
2. Each robot builds a local map.
3. Frontier locations are detected.
4. A coordinator assigns different frontiers to each robot.
5. Robots explore simultaneously.
6. Environmental information is shared.
7. If semantic perception is implemented, Robot 2 detects an object.
8. The object position is stored in a shared world model.
9. Robot 1 can navigate to the object even if Robot 1 never detected it directly.
10. Metrics demonstrate the advantage of coordinated multi-robot exploration.

5. CORE ROS 2 CONCEPTS TO PRACTICE
==================================

The project is also a ROS 2 refresher.

The developer should actively understand and be able to explain:

Nodes
-----
Independent computational units.

Topics
------
Asynchronous streams of data.

Examples:
- /robot1/scan
- /robot1/odom
- /robot2/scan
- /shared/frontiers

Services
--------
Request-response interactions.

Possible examples:
- reset shared map
- save experiment
- request world model snapshot

Actions
-------
Long-running tasks with feedback and cancellation.

Primary example:
- Nav2 NavigateToPose

Parameters
----------
Runtime-configurable values.

Examples:
- robot names
- map resolution
- frontier minimum size
- goal allocation weights
- safety distance
- exploration timeout

Namespaces
----------
Critical for multi-robot separation.

Expected structure:
- /robot1/...
- /robot2/...
- /shared/...

TF2
---
Critical coordinate-frame system.

The developer must understand:
map -> odom -> base_link -> sensors

For a two-robot system, frame collisions must be avoided.

Possible names:
robot1/map
robot1/odom
robot1/base_link
robot1/base_scan

robot2/map
robot2/odom
robot2/base_link
robot2/base_scan

If a shared global map frame is later introduced:
global_map
  -> robot1/map
  -> robot2/map

The transformation between robot-local map frames and the global frame must be explicit.

QoS
---
The developer should understand:
- reliability
- durability
- history
- depth

Sensor streams may use best-effort QoS.
Important state information may use reliable QoS.
Map-like latched data may require appropriate durability settings.

14. PHASE 4 — FRONTIER DETECTION
================================

Objective:
Automatically identify unexplored boundaries.

Definition:
A frontier is a free-space region adjacent to unknown map cells.

Implementation recommendation:
Keep frontier detection algorithm independent from ROS.

Pure function example:
detect_frontiers(occupancy_grid) -> list[Frontier]

Potential algorithm:
1. Iterate over known free cells.
2. Find free cells adjacent to unknown cells.
3. Cluster connected frontier cells.
4. Remove clusters below minimum size.
5. Calculate centroid.
6. Estimate information gain.

Outputs:
- frontier positions
- frontier sizes
- optional information gain

Visualization:
Publish markers to RViz.

Acceptance criteria:
- frontiers appear at boundaries of explored space
- invalid isolated cells are filtered
- frontier centroids are stable enough for navigation
- frontiers are visible in RViz

Unit tests:
- empty map
- fully explored map
- simple room
- two disconnected frontiers
- noise / small clusters


15. PHASE 5 — MULTI-ROBOT FRONTIER ALLOCATION
=============================================

Objective:
Prevent robots from exploring the same location unnecessarily.

Create:
sharednav_coordinator

Coordinator inputs:
- robot poses
- robot navigation states
- detected frontiers
- optional robot path length estimates

Coordinator outputs:
- assigned goal for Robot 1
- assigned goal for Robot 2

Initial cost function:
cost(robot, frontier) = EuclideanDistance(robot, frontier)

Improved cost:
cost =
    w_distance * distance
    - w_information * information_gain
    + w_conflict * conflict_penalty

Rules:
- one frontier cannot be assigned to two robots at the same time
- reassign if navigation fails
- invalidate frontier if it disappears
- do not constantly change goals due to small map updates
- use hysteresis or a minimum goal commitment time

Acceptance criteria:
- Robot 1 and Robot 2 receive different goals
- both explore simultaneously
- failed goals can be reassigned
- duplicated exploration is lower than independent behavior

Learning objective:
Understand:
- task allocation
- centralized coordination
- action clients
- robot status tracking


16. PHASE 6 — SHARED WORLD MODEL
================================

Objective:
Create a common representation that is richer than each individual robot's local view.

Create:
sharednav_world_model

Initial shared state:
- robot poses
- robot status
- frontiers
- optional global occupancy information

Start simple.

Do not implement mathematically complex occupancy fusion immediately.

Version 1 map fusion can:
1. transform robot-local map observations into a shared frame
2. ignore unknown cells
3. combine known free and occupied cells
4. use conservative conflict handling

Example conservative rule:
- if reliable source reports occupied -> mark occupied
- otherwise if at least one source reports free -> mark free
- otherwise -> unknown

IMPORTANT:
The hardest problem is coordinate alignment.
The implementation must clearly document how robot map frames are related.

Possible approaches:
A. Known initial robot poses in common simulation frame.
B. Shared fixed world reference.
C. Later: scan/pose graph alignment.

For the 4-day project, A or B is acceptable.

Acceptance criteria:
- shared representation contains observations from both robots
- robot sources are traceable
- world model updates without crashing when one robot temporarily stops publishing

19. PHASE 9 — BASIC ROUTE CONFLICT HANDLING
==========================================

Stretch feature.

Objective:
Reduce robot-to-robot motion conflicts.

Simple version:
If robots approach the same narrow region:
- coordinator assigns priority
- lower-priority robot pauses or replans

Possible detection:
- compare planned paths
- detect spatial overlap
- optionally estimate arrival-time overlap

Initial rule:
if distance_between_paths < threshold:
    lower_priority_robot waits

Do not attempt full multi-agent trajectory optimization in this project.

Acceptance criteria:
- robots do not repeatedly deadlock in a narrow corridor
- priority decision is logged
- paused robot resumes after conflict disappears

- PEP 8

- small functions

- exceptions handled explicitly

ROS nodes:
- descriptive node names
- descriptive topic names
- parameters declared explicitly
- timers documented
- callback groups only when required
- no unnecessary multithreading

Launch:

- avoid duplicate launch definitions
- reuse sub-launch files

- YAML for tunable parameters
